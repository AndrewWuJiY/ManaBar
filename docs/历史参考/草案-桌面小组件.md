# 桌面小组件方案（WidgetKit + App Group）

> 状态：**方案阶段，尚未实施**。本文只描述改造路径与风险，代码未动。
> 目标：在 macOS 桌面 / 通知中心提供一个系统小组件，显示内容与现有悬浮窗 HUD 对齐。

## 0. 已确认决策

| 项 | 决策 |
| --- | --- |
| 技术路线 | 真 WidgetKit Extension + App Group 共享存储 |
| 尺寸 | **只做 `systemMedium`**（横向长方形，约等于两个 small 并排） |
| 显示内容 | 对齐悬浮窗：Codex + Claude 两行，5h 窗口（无则回退周），进度条 + 剩余百分比 + 重置时间 |
| 主 App 未运行 | **显示「请启动 ManaBar」空态**，不显示过期数据 |
| 点击行为 | `widgetURL` 打开主窗口「用量统计 → 概览」；空态与正常态共用同一 URL |

## 1. 为什么不是「改造悬浮窗」

现有悬浮窗（`Floating/`）是**主进程内的 SwiftUI 视图**：

- `FloatingContentView` 通过 `@Environment(AppState)` 直接拿实时额度
- `FloatingPanelController` 用 `NSPanel` 自管窗口、位置、吸附
- 倒计时靠 `TimelineView(.periodic)` 自走

WidgetKit 小组件是**独立进程的 App Extension**，以上三条全部不成立：

| 维度 | 悬浮窗 | 小组件 |
| --- | --- | --- |
| 数据来源 | `AppState` 内存对象 | 只能读共享存储（文件 / UserDefaults） |
| 刷新时机 | `Scheduler` 驱动，秒级同步 | `TimelineProvider` + 主 App `reloadTimelines` 推送 |
| 能否自己拉额度 | 能 | **不能**（Keychain、token 刷新、CLI 兜底都在主进程） |
| 窗口控制 | 自管 `NSPanel` | 系统托管，App 无权控制位置 / 层级 |
| 自走倒计时 | `TimelineView` | 不可用，需 `Text(timerInterval:)` |
| 右键菜单 | `.contextMenu` | 不支持，只有 `widgetURL` / `Button(intent:)` |

所以小组件是**新开一条只读数据通路**，悬浮窗保持原样、继续作为实时视图存在，两者共用视图组件而非共用实现。

## 2. 数据流

```
Scheduler → AppState.refresh*Quota()
              ↓ 成功
         saveQuotaCache()                    ← Core/AppState.swift:524 唯一收口点
              ↓ 写快照 + 心跳
    App Group 容器 / quota-cache.json + widget-state.json
              ↓
   WidgetCenter.reloadTimelines()
              ↓
   ManaBarWidget TimelineProvider → [数据 entry, 到期空态 entry] → View
```

关键点：

- `saveQuotaCache()` 是全项目唯一的缓存落盘点，主副 Codex 账号、Claude 都走它，是理想的 reload 注入位置。
- 主 App 常驻菜单栏（`LSUIElement`），这条推送链路在正常使用场景下是稳的。
- 主 App 停止后小组件如何自动翻空态，见 §4。

## 3. 改造清单

### 3.1 共享层抽取

现状问题：小组件要复用的组件散落在三处，且都带主进程依赖。

| 需要的东西 | 现位置 | 依赖问题 |
| --- | --- | --- |
| `QuotaWindow` / `QuotaSnapshot` | `Core/Quota/QuotaModels.swift` | 纯 Codable，可直接共享 |
| `QuotaCacheRecord` / `QuotaCachePayload` | `Core/Storage/QuotaCache.swift` | 同上，`cacheFileURL()` 需改造（§3.2） |
| `ServiceTile` / `ProgressBar` / `statusColor` / `Color` 扩展 | `Main/DesignSystem.swift`（467 行） | 文件内 321–347 行依赖 `SettingsStore.shared` |
| `tr()` / `formatResetCompact()` | `Core/L10n.swift` | `tr()` 读全局 `_cachedLanguage`，由 `SettingsStore` 播种 |
| `FloatingRow` 行布局 | `Floating/FloatingContentView.swift` | 依赖 `@Environment(AppState)` 的是外层 `FloatingContentView`，`FloatingRow` 本身已是纯数据驱动 |

实际做法（已落地）：

1. 新建 `Shared/` 目录放两个 target 都编译的文件：`WidgetSharedState.swift`（心跳 + 显示开关）、`QuotaVisuals.swift`（视觉元素）。不整体搬运 `DesignSystem.swift`，它含大量主窗口专用组件。
2. 从 `DesignSystem.swift` 迁出三块到 `Shared/QuotaVisuals.swift`：`statusColor` + 4 档状态色 + `quotaAdaptiveColor`、`ServiceTile` + `LogoCache`、`ProgressBar`。`quotaAdaptiveColor` 由 file-private 放开一级——原文件的 `Color.connectedStatus` 仍要用它。`VisualEffectBackground` 不抽，小组件不能用（§3.5）。
3. **`FloatingRow` 不提升**（与初版方案的调整）。悬浮窗容器 168pt、小组件 medium 约 330pt，同一套 Row 硬套过去会一头堆一头留白，强行共享反而要塞进一堆布局分支。改为**共享元素、各自排版**：两边都用同一个 `ServiceTile` / `ProgressBar` / `statusColor`，行布局各写各的。视觉一致性由元素保证，也避免了对 `Floating/` 的无谓改动。
4. **`L10n.swift` 不抽**。小组件文案只有空态两行，`tr()` 依赖的 `_cachedLanguage` 由 `SettingsStore` 播种，抽它要连带拆 `L10n` / `formatResetHint`，不划算。改为在 `WidgetSharedState.language` 里带 `"zh"` / `"en"`，小组件按 `entry.zh` 选词。重置时间也不用 `formatResetCompact`——小组件必须用系统自更新的 `Text(timerInterval:)`（§3.3）。
5. 品牌色 `CodexAccent` / `ClaudeAccent` 的 colorset **复制**了一份到 `ManaBarWidget/Assets.xcassets`。小组件是独立 bundle，读不到主 App 的 Asset Catalog；`Resources/Logos/*.svg` 同理，需要勾进 Widget target 的 Copy Bundle Resources（`LogoCache` 走 `Bundle.main`，在 extension 里指向 appex 自身）。**代价**：品牌色有两份定义，改色要改两处，两边文件头都写了互相指向的注释。

### 3.2 App Group 与存储迁移

- Group ID：`group.659P79368S.com.andrewwujiy.manabar`。**实测**：在 Signing & Capabilities 里填 `659P79368S.com.andrewwujiy.manabar`，Xcode 会自动补上 `group.` 前缀，最终写进 entitlements 的是带前缀的完整串。`QuotaCache.appGroupID` 必须与 entitlements 里的字符串逐字一致。
- 主 App `ManaBar.entitlements`：**保持 `app-sandbox = false`**，仅追加 `com.apple.security.application-groups`。非沙盒进程加 App Group entitlement 是合法的，`containerURL(forSecurityApplicationGroupIdentifier:)` 会返回 `~/Library/Group Containers/group.659P79368S.com.andrewwujiy.manabar/`。
- 新建 `ManaBarWidget.entitlements`：`app-sandbox = true` + 同一个 group。
- `QuotaCache.cacheFileURL()` 改造：优先 group container，取不到时回退现有 `~/Library/Application Support/ManaBar/`。首次启动做一次单向迁移（旧文件存在且新位置无文件 → 拷过去，旧文件保留不删，便于回滚）。

配置项（语言、`floatingShowCodex/Claude`、`floatingShowReset`、`resetTimeDisplay`）小组件也要读。两种做法：

- **A. 迁移 `SettingsStore` 到 `UserDefaults(suiteName:)`** —— 干净，但 375 行的 `Settings.swift` 全量迁移 + 已有的 `ccbar → manabar` 迁移逻辑要再套一层，风险面大。
- **B. 镜像写一份 widget 专用状态** —— 落盘时顺带把那几个键 + 心跳写进 group 容器的 `widget-state.json`。改动局限在一个函数，主 App 设置逻辑零改动。**推荐 B**，等小组件稳定后再考虑要不要做 A。

### 3.3 Widget Extension target

- Target 名 `ManaBarWidget`，Bundle ID `com.andrewwujiy.manabar.widget`，Deployment Target 跟主 App 14.0。
- `TimelineProvider`：
  - `getTimeline` 读共享缓存 + 心跳 → 生成 entry 序列（§4）
  - 不要在 Provider 里发任何网络请求
- **尺寸只支持 `systemMedium`**，通过 `.supportedFamilies([.systemMedium])` 显式限定。理由：两个服务各占一行、每行要放 tile + 进度条 + 百分比 + 重置时间，`systemSmall`（正方形）放不下重置时间，会退化成悬浮窗的阉割版，没有存在价值；`systemLarge` 对这个数据量是浪费。
- 倒计时：`TimelineView(.periodic)` 在小组件里**不工作**。但 `Text(date, style:)` 系列也不能用——见 §3.7。最终方案是静态文本 + 多 entry 推进。

### 3.4 medium 布局（已定稿）

悬浮窗容器 `minWidth: 168pt`，而 `systemMedium` 约 330×155pt。直接照搬会左侧堆一坨、右侧大片留白。

定稿参数：

| 元素 | 值 | 说明 |
| --- | --- | --- |
| 百分比 | 26pt semibold, monospacedDigit | **主信息，必须是视觉焦点** |
| ServiceTile | 34pt，logo 21pt，圆角 10pt | 圆角与容器大圆角呼应（Liquid Glass 的同心原则），5pt 会显得太方 |
| 服务名 | 13pt medium, secondary | 标签，不是主角 |
| 重置时间 | 11pt medium, secondary 0.8 | `· 4h25m`，跟在服务名后面 |
| 进度条 | 9pt 高 | **独占整行**，右端与百分比对齐 |
| 行距 | 两行之间 Spacer(min 16)，上下各一个 Spacer | 内容撑满容器而非居中堆叠 |

一条教训：初版把百分比压到 15pt、和 11pt 服务名挤一行，整块内容只占约 55pt 高，容器却有 155pt——**看着"空"的根因不是背景大，是内容没撑起来**。放大层级差比加装饰有效。

刻意**不**给每行加卡片背景或玻璃层：`CLAUDE.md` 实现约束写明不自造大面积背景与玻璃阴影，密度问题靠排版解决。

### 3.7 两个必须记住的坑

**一、`Text(date, style:)` 会挤垮同行布局。**

小组件里不能用 `TimelineView`，自然会想到用系统自更新的日期文本。但这类 Text 的**固有宽度在布局期是不确定的**（系统要为最长可能文案预留），放进 `HStack` 会有两种结局：

- 给它固定宽度（`.frame(width: 58)`）→ 中文 `.relative` 输出"4小时 32分钟"，被截断成"4小时…"
- 给它 `.fixedSize()` → 它抢走超额宽度，把同行的服务名和百分比**压成 0 宽**，文字溢出到 tile 底下，整行视觉崩塌

最终方案：重置时间用 `compactRelativeReset` 生成**静态文本**（`4h25m`，宽度可算），走动交给 timeline——每 3 分钟埋一个 entry，每个 entry 用自己的 `date` 当"现在"计算倒计时，一直铺到心跳失效那一刻。这样即使主 App 卡住不 reload，倒计时照样推进，末尾的空态 entry 也还在。

**二、改了 widget 代码后，桌面上的小组件还在跑旧二进制。**

⌘R 重装了 App，但系统已加载的 widget extension 不一定马上换新代码，经常还用旧的渲染一阵，看起来像"改动没生效"。确认代码已改却看不到变化时，把桌面上的小组件**删掉重新拖一个**，强制系统重新加载 extension。

### 3.5 视觉差异（照搬悬浮窗时必须改的地方）

`FloatingContentView` 的背景三层叠加（`windowBackgroundColor` + `.popover` material + hairline 描边）在小组件里**整套不能用**：

- 小组件背景由系统提供，必须用 `.containerBackground(for: .widget)`，自绘背景会出现双层材质和圆角错位。
- `VisualEffectBackground`（`NSVisualEffectView`）在 extension 沙盒里行为不可靠。
- macOS Sonoma 桌面小组件在用户点击桌面时会**去饱和至近单色**。交通灯状态色（绿/黄/橙/红）此时几乎失效 → `<20%` 和 `=0` 档需加形状或符号冗余（SF Symbol 叹号等），不要只靠颜色传递状态。这一条落地时同步进 `docs/设计风格.md`。

### 3.6 主 App 注入

`Core/AppState.swift` 的 `saveQuotaCache()` 内，落盘成功后追加：

```swift
WidgetCenter.shared.reloadTimelines(ofKind: "ManaBarQuotaWidget")
```

注意节流：该函数在主副 Codex 账号各自刷新时都会被调用，一轮刷新可能触发多次。建议比对快照是否实际变化，无变化不 reload。

## 4. 「请启动 ManaBar」空态

这是本次方案里唯一需要新设计的机制。难点在于：**主 App 退出时没有机会通知小组件**（被强杀或崩溃时更是如此），而小组件的 timeline 是提前生成的，不会主动重算。

### 4.1 心跳 + 预埋翻转 entry

1. 主 App 向 group 容器的 `widget-state.json` 写心跳时间戳 `heartbeatAt`。写入时机：App 启动、每次 `saveQuotaCache()`、以及一个**固定 5 分钟的独立 reload 心跳**（不跟 `quotaInterval` 抖，参照 `Scheduler.serviceStatusInterval` 的既有做法）。
2. `getTimeline` 生成**两个 entry**：
   - `entry[0]` = 当前时刻，正常数据态
   - `entry[1]` = `heartbeatAt + staleThreshold`，空态
   - policy = `.after(entry[1])`
3. 主 App 在跑 → 每 5 分钟 reload 一次，`entry[1]` 被不断推后，用户永远看不到空态。
4. 主 App 停了 → 没有新的 reload，时间走到 `entry[1]`，小组件**自动翻成空态**，无需任何进程配合。

### 4.2 阈值取值

`quotaInterval` 可选 1 / 2 / 3 / 5 / 10 分钟（默认 2 分钟，无「手动」档），所以不能用它当心跳基准——10 分钟档下阈值会被迫拉到 20 分钟以上。用独立的 5 分钟 reload 心跳，`staleThreshold` 取 **13 分钟**（5 × 2 + 3 分钟宽限），可容忍一次心跳丢失。

风险：5 分钟一次 `reloadTimelines` 是否超预算需实测。macOS 桌面小组件的刷新预算比 iOS 宽松得多，预期没问题，但这是 P1 阶段必须验证的点。若超预算，退化为 10 分钟心跳 + 23 分钟阈值。

### 4.3 空态内容

- SF Symbol + `tr("ManaBar isn't running", "ManaBar 未运行")` + 次级说明 `tr("Click to launch", "点按启动")`
- 整块套 `widgetURL`，点击拉起主 App（`LSUIElement` App 被 URL 唤起后不会抢焦点，行为自然）
- **不显示任何百分比数字**，避免用户误读为实时额度——这正是选空态而非过期数据的理由，不要在空态里偷偷留旧数字。

### 4.4 首次安装态

用户刚添加小组件、主 App 从未运行过时，group 容器内无缓存文件。走同一套空态即可，文案不区分。

## 5. URL Scheme 与跳转

现状：项目**完全没有 URL scheme**——`Info.plist` 无 `CFBundleURLTypes`，代码里无 `onOpenURL`、无 `application(_:open:)`。这是本次新增的能力，属于配置行为变更，落地时需同步 `技术实现.md`。

### 5.1 实现路径

1. `Info.plist` 新增 `CFBundleURLTypes`，scheme 取 `manabar`（独特性足够，冲突风险低）。
2. 小组件侧：`.widgetURL(URL(string: "manabar://stats"))` 套在整块内容上。
3. 主 App 侧在 `AppDelegate` 实现 `application(_ application: NSApplication, open urls: [URL])`。**不要用 SwiftUI 的 `onOpenURL`**——本 App 的根场景是 `MenuBarExtra`，`onOpenURL` 挂在其中的行为不稳，`AppDelegate` 是确定的。
   `AppDelegate` 拿不到 `AppState`（后者是 `ManaBarApp` 的 `@State`），照抄 `FloatingPanelController.attach` 的既有模式，由 `ManaBarApp` 的 `.task` 注入一个 weak static 引用。冷启动时 URL 会早于 scene 的 `.task` 到达，所以注入前先把 URL 存进 `pendingURL`，注入后立刻补发，否则冷启动那一次点击会丢。
4. 处理逻辑直接复用现有通路，不新造机制：

```swift
NSApp.activate(ignoringOtherApps: true)
appState.mainTab = .stats
appState.shouldOpenMainWindow = true   // ManaBarApp.swift:54 的 onChange 会接管 openWindow
```

### 5.2 「概览」落点的已知偏差

`StatsView` 的 `viewMode`（概览 / 时间线 / 明细）是 **View 私有 `@State`，默认 `.overview`**（`Main/StatsView.swift:165`），外部拿不到也设不了。因此：

- 主窗口**未打开**时点小组件 → 窗口新建，落在概览。符合预期。
- 主窗口**已打开且停在「明细」**时点小组件 → 只把窗口拉到前台，仍停在明细页，**不会跳回概览**。

两种处理：

- **A. 接受现状（推荐）** —— 零改动。用户手动切到明细后又去点小组件的场景很边缘，为它把一个纯 UI 局部状态提升为全局状态不划算，也违反「不做无关重构」。
- **B. 强制回概览** —— 把 `viewMode` 提升到 `AppState`，或加一个一次性的 `requestedStatsMode` 请求字段，URL 处理时置位。改动不大但触碰 `StatsView` 的状态归属，需要连带检查其他入口（⌘1、Popover）的行为一致性。

未另行确认则按 A 实施。

### 5.3 空态与冷启动

空态和正常态**共用同一个 URL**，不需要两套：

- App 未运行时，系统会因 URL 先拉起 App，URL 在 `applicationDidFinishLaunching` 之后到达，此时直接 `openWindow` 即可，额度数据由 `bootstrap()` 异步填充，主窗口自身已有加载态。
- 这也是空态「点按启动」的实现——不必为空态单独设计一条唤起路径。
- `LSUIElement` App 被 URL 唤起后需要显式 `NSApp.activate`，否则窗口会开在后台。

## 6. 签名与发布

这是本方案**唯一可能卡住的环节**，且必须本人操作：

1. ~~developer.apple.com 手动建 App Group~~ —— **实测不需要**。在 Xcode 的 Signing & Capabilities 里加 App Groups 并填 ID，自动签名会替你在开发者账号注册，Provisioning Profile 自动变为 Xcode Managed Profile。
2. 本项目用的是 **Personal Team（免费账号）**，实测**可以**使用 App Groups capability，不受限制。
3. 两个 target 都要加：主 App 加完后，Widget target 也要 + Capability → App Groups 并**勾选**同一个 group（不勾等于没配，entitlements 里不会出现 `application-groups`）。
4. `发布.command` 的 `xcodebuild` 会自动编译并嵌入 extension 到 `Contents/PlugIns/`，但**公证需要整包验证**——首次发布前必须实跑一遍 `notarytool`，确认 extension 一并通过。
5. 用户侧：桌面小组件要求 App 位于 `/Applications`，且首次需在「编辑小组件」面板里手动添加。README 安装说明要补一段。

## 7. 风险清单

1. ~~App Group profile 拉取失败~~ —— **已验证通过**。Personal Team 下 Xcode 自动注册成功，App 首次运行后 `~/Library/Group Containers/group.659P79368S.com.andrewwujiy.manabar/` 由系统自动创建，`containerURL` 返回有效路径。
2. **公证链路** —— 优先级下调。本项目实际用 Apple Development 证书签名，README 指引用户 `xattr -d com.apple.quarantine` 绕 Gatekeeper，并未走公证流程，故「嵌套 extension 能否通过公证」暂不构成风险。若将来转 Developer ID + 公证，需重新验证 `Contents/PlugIns/` 下的 appex 是否一并通过。
3. **reload 预算** —— 5 分钟心跳是否可持续，见 §4.2。
4. **单色化** —— 见 §3.5，设计层面解决，不是 bug。
5. **medium 留白** —— 见 §3.4，照搬悬浮窗布局会不成立，需要重新排版。
